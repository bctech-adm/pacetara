# Keputusan teknis

Catat setiap keputusan baru di bawah, dengan tanggal dan modul. Jangan ubah keputusan lama tanpa mencatat alasannya.

## Modul 1.1 Fondasi (10 Nov 2026)

1. **Akses database: `pg` + migrasi SQL mentah.** Tanpa ORM, karena PostGIS (geometry, fungsi spasial) lebih jelas ditulis dalam SQL. Migrasi berupa file `backend/migrations/NNNN_nama.sql`, dicatat di tabel `schema_migrations` beserta checksum, setiap file dijalankan dalam satu transaksi dengan advisory lock. Query builder (mis. Kysely) boleh ditambahkan di modul berikutnya bila perlu.
2. **Backend ESM + NestJS 12 + Vitest.** NestJS 12 hanya tersedia sebagai ESM, jadi backend memakai `"type": "module"` dan import berakhiran `.js`. Tes memakai Vitest dengan plugin SWC, karena esbuild tidak menghasilkan metadata dekorator yang dibutuhkan DI Nest. TypeScript dikunci di 5.9 karena TypeScript 7 (port native) belum didukung ekosistem tooling.
3. **API dan worker satu basis kode.** `backend/` menghasilkan satu image; service `api`, `worker`, dan `migrate` di Compose hanya beda perintah.
4. **Antrean: BullMQ di atas Redis.** Redis berjalan dengan `noeviction` agar job tidak hilang.
5. **Enkripsi kolom di aplikasi, bukan pgcrypto.** `FieldCrypto` memakai AES-256-GCM dengan format `v1 | iv(12) | tag(16) | ciphertext` dan AAD (mis. `users.email:<id>`) agar ciphertext tidak bisa dipindah antar baris. Byte versi memungkinkan rotasi kunci. Kunci tidak pernah masuk ke database atau query SQL.
6. **Blind index** untuk email dan nomor HP: HMAC-SHA256 dengan kunci terpisah (`BLIND_INDEX_KEY`) atas nilai yang dinormalisasi (email huruf kecil + trim, nomor HP format E.164 `+62…`). NIK memakai fungsi yang sama dengan konteks `nik` (HMAC berkunci, bukan hash biasa yang bisa di-brute force).
7. **Reverse proxy: Caddy.** HTTPS otomatis, TLS 1.2+ (TLS 1.1 ditolak, sudah diuji), HTTP diarahkan ke HTTPS, HSTS. Log akses tidak mencatat query string, `Authorization`, atau `Cookie`. Untuk lokal, domain `*.localhost` memakai CA internal Caddy. Port bisa diatur (`HTTP_PORT`, `HTTPS_PORT`) karena VPS dipakai bersama.
8. **Panel admin: Vite + React + TypeScript**, dibangun menjadi file statis dan disajikan container Caddy kecil dengan CSP ketat. URL API disuntikkan saat runtime (`config.js` dirender dari env `API_PUBLIC_URL`), jadi satu image bisa dipakai di semua lingkungan.
9. **wa-otp: layanan HTTP internal** dengan antarmuka `OtpProvider` (`BaileysProvider` sekarang, `CloudApiProvider` nanti, dipilih lewat `WA_PROVIDER`). API memanggil `POST /send` dengan header `X-Shared-Secret`. Selain 204, API (modul 1.2) wajib beralih ke OTP email. Login sesi lewat QR di log container atau kode pairing (`WA_PAIRING_NUMBER`). Nomor HP di log selalu disamarkan.
10. **Cadangan:** `pg_dump -Fc` → dienkripsi dengan `age` (public key di `.env`, private key tidak pernah di VPS) → diunggah dengan `rclone` ke remote di luar VPS. Data penyimpanan objek ikut dicadangkan sebagai tar terenkripsi. Diuji lokal: backup → hapus data → restore mengembalikan data dan PostGIS. Unggah ke remote belum diuji karena remote belum disiapkan.
11. **Certificate pinning ke CA, bukan ke leaf.** Dart `HttpClient` tidak memakai Network Security Config Android dan tidak memberi akses ke rantai sertifikat, jadi pin SPKI intermediate tidak praktis. Aplikasi memakai `SecurityContext(withTrustedRoots: false)` yang hanya mempercayai ISRG Root X1 dan X2 (berlaku sampai 2035 dan 2040). Caddy dikunci ke ACME Let's Encrypt (`acme_ca`) agar tidak beralih ke ZeroSSL. Mengganti CA berarti merilis aplikasi dengan root baru lebih dulu.
12. **Flutter:** Riverpod 3 (state), go_router (navigasi), dio (HTTP), flutter_secure_storage (Keystore). Base URL API lewat `--dart-define=API_BASE_URL`; build rilis menolak http dan alamat IP.
13. **Versi Node: 22 LTS** di image dan CI.
14. **Penyimpanan objek: SeaweedFS, bukan MinIO.** Per November 2026 image resmi MinIO (`minio/minio`, `minio/mc`, juga di quay.io) tidak lagi tersedia karena MinIO berhenti merilis build komunitas. Fork pihak ketiga tidak dipakai karena risiko rantai pasok. SeaweedFS (`chrislusf/seaweedfs`, Apache 2.0, image resmi pengelolanya) menyediakan API S3, jadi kode aplikasi memakai klien S3 biasa dan bisa pindah ke penyedia S3 lain hanya dengan mengubah `S3_ENDPOINT`. Versi image dikunci (`4.53`). Bucket privat dibuat oleh service `s3-init`.
15. **Healthcheck Postgres lewat TCP** (`pg_isready -h 127.0.0.1`). Saat inisialisasi pertama, server sementara hanya mendengarkan socket, sehingga healthcheck lewat socket lolos terlalu cepat dan migrasi gagal.
16. **Jaringan Docker:** `internal` (tanpa akses internet) untuk Postgres, Redis, S3; `edge` untuk layanan yang butuh keluar (API, worker, wa-otp, backup) atau menerima koneksi masuk (Caddy). Hanya Caddy yang mem-publish port. Container backend berjalan `read_only` dengan `no-new-privileges`.
17. **Catatan Windows (development):** jalankan Vitest dari path dengan huruf drive besar (`E:\...`). Jika shell memakai `e:\`, Vitest memuat dirinya dua kali dan gagal dengan "failed to find the runner". Tidak terjadi di CI (Linux).

## Deploy pertama (10 Nov 2026)

18. **VPS bersama memakai Traefik yang sudah ada, bukan Caddy.** Port 80/443 di VPS Hostinger dipegang Traefik (file provider saja, CrowdSec, resolver `le-http`). PaceTara dijalankan dengan `docker-compose.vps.yml` yang menonaktifkan Caddy dan menyambungkan `pacetara-api` serta `pacetara-admin` ke network `web-edge`. Rute ada di `infra/traefik/pacetara.yml`, dipasang ke `/opt/infra/traefik/dynamic/clients/pacetara.yml` lalu `docker exec traefik kill -HUP 1`. Stack ada di `/opt/infra/web/clients/pacetara`. Di VPS khusus nanti, cukup `docker-compose.yml` saja (Caddy aktif lagi).
19. **Pin juga root Let's Encrypt generasi Y (Root YE, Root YR).** Sertifikat produksi diterbitkan intermediate YE2 → Root YE, yang saat ini di-cross-sign oleh ISRG X2 → X1. Rantai diverifikasi lolos baik terhadap X1/X2 maupun Root YE saja, jadi aplikasi tetap tersambung setelah cross-sign dicabut.
20. **Image sementara dikirim manual** (`docker save` → `scp` → `docker load`, tag = commit) karena repo belum punya remote GitHub. Setelah remote dan GHCR siap, ganti `REGISTRY`/`IMAGE_TAG` di `.env` VPS dan pakai `docker compose pull`.
21. **Kunci cadangan:** public key age ada di `.env` VPS; private key di laptop pemilik (`%USERPROFILE%\pacetara-backup-age.key`). Pindahkan ke pengelola kata sandi; tanpa kunci itu cadangan tidak bisa dipulihkan.

## Modul 1.2 Akun dan login (10 Nov 2026)

22. **Token:** akses = JWT HS256 15 menit berisi `sid` (id family sesi); penyegar = 32 byte acak, hanya SHA-256-nya disimpan, dirotasi setiap dipakai, umur 30 hari. Memakai token penyegar yang sudah dirotasi = indikasi pencurian → seluruh family dicabut. Family yang dicabut dicatat di Redis selama umur token akses, sehingga logout/hapus akun/reset kata sandi langsung menolak token akses yang masih berlaku. Aplikasi wajib me-refresh satu per satu (single-flight), karena dua refresh paralel akan dianggap pemakaian ulang.
23. **Guard global:** semua endpoint wajib token akses kecuali yang ditandai `@Public()` (health, config, register, login, google, refresh, lupa/atur ulang kata sandi). Endpoint baru otomatis terlindungi.
24. **Kata sandi:** Argon2id via `@node-rs/argon2` (prebuilt, tanpa install script), parameter OWASP m=19 MiB, t=2, p=1. Login dengan email tak terdaftar tetap menjalankan verifikasi hash palsu agar waktu respons sama. Pesan galat sama untuk email salah dan kata sandi salah.
25. **Kode verifikasi:** 6 digit, disimpan sebagai HMAC berkunci (kunci diturunkan dari `BLIND_INDEX_KEY`), target (email/HP) disimpan terenkripsi. Sekali pakai, 5 kali salah lalu hangus, jeda kirim ulang 60 detik, maksimal 5 kode/jam per tujuan. Berlaku 10 menit (email) atau 5 menit (WhatsApp).
26. **OTP nomor HP:** WhatsApp lebih dulu; setiap respons wa-otp selain 204 (atau timeout 8 detik) → kode baru dikirim ke **email akun yang sudah terverifikasi**. Jika email belum terverifikasi, cadangan ditolak (503 `otp_unavailable`) agar kode tidak dikirim ke alamat yang belum dibuktikan. Karena itu urutan di aplikasi: verifikasi email dulu, baru nomor HP.
27. **Level 1 dihitung database** (trigger `users_compute_level`): email dan HP terverifikasi = 1. Level 2 tidak diturunkan oleh trigger.
28. **Login Google:** ID token diverifikasi di server (`google-auth-library`, `aud` ∈ `GOOGLE_CLIENT_IDS`). Akun baru wajib persetujuan privasi (428 `privacy_required`). Menautkan Google ke akun email yang sudah ada hanya jika Google menyatakan `email_verified`, untuk mencegah pengambilalihan akun.
29. **Kebijakan privasi berversi** (`PRIVACY_POLICY_VERSION`). Pendaftaran wajib mengirim versi yang sama dengan server; jika naskah diperbarui, versi lama ditolak (428 `privacy_outdated`).
30. **Hapus akun = anonimisasi**, bukan DELETE baris: semua data pribadi di-NULL-kan, nama menjadi "Pengguna dihapus", token dan kode dihapus, foto dihapus dari penyimpanan. Constraint `users_deleted_is_anonymous` memaksa tidak ada data pribadi tersisa pada akun berstatus `deleted`. Email dan nomor HP bisa dipakai lagi untuk akun baru. Modul berikutnya wajib menambah langkahnya sendiri di `UsersService.deleteAccount` (chat pribadi, lari, dsb.).
31. **Foto profil:** jenis dicek dari isi berkas (sharp), maks 8 MB dan 50 MP, di-encode ulang ke WebP 512 px sehingga seluruh EXIF/GPS terbuang. Tidak ada URL S3 publik: aplikasi mengambil `/v1/users/:id/avatar` dengan token, lewat Dio yang ber-pinning (bukan `Image.network`, yang tidak memakai pinning).
32. **Email:** SMTP via nodemailer, STARTTLS wajib di produksi. Lokal memakai Mailpit (`docker compose --profile dev up`, UI di http://127.0.0.1:8025).
33. **Tes e2e** (`backend/test/*.e2e.spec.ts`) memakai Postgres+PostGIS dan Redis sungguhan (`TEST_DATABASE_URL`, `TEST_REDIS_URL`), dengan email/WhatsApp/Google/S3 dipalsukan. Tanpa variabel itu suite dilewati. CI menjalankannya di job "Migrasi + tes e2e".
34. **gitleaks di CI** dijalankan sebagai CLI atas seluruh riwayat, karena gitleaks-action gagal pada push pertama ke repo kosong (tidak memindai apa pun tetapi tetap merah).

## Pengerasan image (10 Nov 2026)

35. **Gerbang Trivy di CI** (HIGH/CRITICAL yang sudah ada perbaikannya) memblokir push image. Pemindaian pertama menemukan: npm bawaan `node:22-alpine` (10 HIGH, bukan dependensi aplikasi), `gosu` di image server `postgres` (26, termasuk 1 CRITICAL), dan `golang.org/x/net` di Caddy v2.11.9 (1 HIGH, belum diperbaiki di rilis Caddy mana pun). Perbaikannya:
    - Runtime Node (backend, wa-otp): `apk upgrade` + npm, npx, corepack dihapus. Perintah container memanggil `node` langsung, jadi npm tidak dibutuhkan.
    - Backup: `alpine:3.24` + `postgresql16-client` (pg_dump/pg_restore 16.15), bukan image server postgres. Backup → restore diuji ulang.
    - Panel admin: Caddy diganti nginx dari `alpine:3.24`, berjalan sebagai user `nginx` (non-root). `config.js` dan CSP ditulis `admin/entrypoint.sh` dari `API_PUBLIC_URL` (divalidasi ketat: hanya `https://domain[:port]`). Menggantikan keputusan #8 (directive templates Caddy).
    - Semua image akhir menjalankan `apk upgrade` agar patch Alpine terbaru ikut walau base image tertinggal.
36. **Action pihak ketiga di CI dikunci ke commit SHA** (mulai dari trivy-action v0.36.0), karena tag bisa dipindah ke kode lain.

## Modul 1.3 Komunitas (10 Nov 2026)

41. **Semua angka batas paket ada di satu file:** `backend/src/plans/plans.ts`. Angkanya mengikuti tabel PRD (pelari gratis bergabung maks. 3 komunitas; komunitas gratis maks. 3 anggota, Pro 30, Pro Unlimited tanpa batas; akun gratis memiliki maks. 1 komunitas gratis). Kontradiksi PRD (A2: angka 50) dan saran B1 (batas gratis lebih besar) **belum diputuskan pemilik**; mengubahnya cukup di file itu.
42. **Cara menghitung batas:** komunitas yang dimiliki ikut dihitung dalam batas bergabung pelari. Komunitas Pro tidak dihitung dalam batas "1 komunitas gratis per akun", sehingga admin bisa punya lebih dari satu komunitas asalkan yang lain Pro (PRD: "sesuai langganan per komunitas"). Permintaan bergabung yang menunggu tidak dihitung; batas diperiksa ulang saat admin menyetujui.
43. **Batas ditegakkan di dalam transaksi dengan kunci baris** (`SELECT … FOR UPDATE`), urutan kunci selalu baris pengguna → baris komunitas agar tidak deadlock. `communities.member_count` dijaga di transaksi yang sama. Diuji: 8 permintaan bergabung bersamaan ke komunitas gratis → tepat 2 berhasil.
44. **Galat batas** selalu `403 limit_reached` dengan `limit.kind` (`user_join`, `community_members`, `owned_communities`, `multi_admin`) dan `limit.max`. Aplikasi menampilkan dialog batas dengan ajakan upgrade (iklan internal PRD 2.5).
45. **Paket berakhir:** data tidak dihapus. Komunitas di atas batas paketnya tidak bisa menerima anggota baru (dari jalur mana pun: gabung, kode, persetujuan). Admin yang sudah ada tetap admin, tetapi admin baru tidak bisa diangkat sampai berlangganan lagi.
46. **Tingkat verifikasi:** semua endpoint komunitas mewajibkan Level 1 (`LevelGuard`). PRD menyebut pemilik komunitas wajib Level 2 (KTP), tetapi Level 2 baru ada di modul 3.1; saat itu tiba, pasang `@RequireLevel(2)` pada pembuatan komunitas dan putuskan nasib komunitas yang sudah ada.
47. **Peran:** pemilik (tepat satu, dijaga unique index), admin (khusus Pro), anggota. Hanya pemilik yang mengangkat/menurunkan admin, mengeluarkan admin, menyerahkan kepemilikan, dan menghapus komunitas. Pemilik tidak bisa keluar sebelum menyerahkan kepemilikan.
48. **Status anggota:** `active`, `pending` (menunggu persetujuan), `banned`. "Keluarkan" menghapus baris (bisa bergabung lagi); "keluarkan dan blokir" menyimpan status `banned`: tidak bisa bergabung lewat jalur mana pun, dan komunitas tampil seolah tidak ada baginya.
49. **Visibilitas:** komunitas privat tetap tampil di direktori (nama, kota, deskripsi, logo, jumlah anggota), tetapi daftar anggota hanya untuk anggota aktif, dan daftar permintaan/blokir hanya untuk admin.
50. **Kode undangan:** 8 karakter dari alfabet tanpa huruf mirip (tanpa 0/O/1/I/L), berlaku 1–30 hari, opsional batas pemakaian, bisa dicabut. Pratinjau dan pemakaian kode dibatasi 10/menit per IP agar tidak bisa ditebak. Tautan `https://pace.bimacreative.tech/j/KODE` saat ini membuka halaman petunjuk di situs publik; App Links Android (`assetlinks.json` + intent filter) menyusul agar tautan langsung membuka aplikasi.
51. **Undangan langsung ke pengguna tertentu ditunda** ke modul 1.6/1.9: belum ada cara mencari pengguna lain tanpa membuka data pribadi (tidak ada pencarian email/HP demi privasi). Untuk sekarang admin membagikan kode/tautan.
52. **Profil dan foto pengguna lain hanya terlihat oleh sesama anggota aktif satu komunitas** (PRD Akses). Modul chat (1.6) perlu meninjau ulang aturan ini untuk chat pribadi.
53. **Hapus akun:** pemilik komunitas yang masih beranggota lain ditolak (`409 owns_communities`) sampai kepemilikan diserahkan atau komunitas dihapus. Komunitas yang hanya berisi pemiliknya ikut terhapus. Keanggotaan lain dihapus dan jumlah anggota disesuaikan.

## APK uji dan deploy otomatis (10 Nov 2026)

54. **Repo GitHub publik** (keputusan pemilik). Konsekuensinya: tidak boleh ada rahasia, alamat internal, atau data pengguna di repo; gitleaks di CI wajib tetap hijau.
55. **Kunci tanda tangan APK:** keystore PKCS12 RSA 4096 `pacetara-upload.jks`, alias `pacetara`, disimpan di luar repo (`%USERPROFILE%`, akses hanya akun pemilik) dan di GitHub Secrets (`PACETARA_KEYSTORE_B64`, `PACETARA_KEYSTORE_PASSWORD`). Kunci ini juga dipakai sebagai *upload key* Play Store nanti. Kehilangan kunci = pengguna harus uninstall untuk memasang versi baru, jadi simpan cadangannya di pengelola kata sandi. SHA-1 kunci ini harus terdaftar sebagai Client ID OAuth Android agar login Google berfungsi di APK rilis.
56. **Distribusi APK uji di luar Play Store:** CI (job `android`) membangun APK bertanda tangan setiap push ke `main` yang lolos tes, lalu menerbitkan GitHub Release `android-<versionCode>` berisi APK dan `latest.json`. `versionCode = 100 + nomor run CI` (selalu naik). API menyajikan `latest.json` di `GET /v1/app/android/latest` (cache 1 menit, hanya menerima URL APK dari rilis repo ini).
57. **Pembaruan di dalam aplikasi:** aplikasi membaca versi terbaru lewat API (koneksi ber-pinning), mengunduh APK dari GitHub dengan TLS biasa (GitHub bukan Let's Encrypt), memverifikasi SHA-256 dari API, lalu membuka penginstal Android. Android juga menolak APK yang ditandatangani kunci lain. Izin `REQUEST_INSTALL_PACKAGES` **harus dihapus** saat rilis di Play Store (kebijakan Play), beserta fitur pembaruan mandiri ini.
58. **Deploy otomatis berbasis tarik** (keputusan pemilik): container `pacetara-deployer` di VPS (`infra/deployer/deploy-loop.sh`) menarik image `latest` dari GHCR setiap 5 menit dan menjalankan ulang layanan yang image-nya berubah, termasuk migrasi. GitHub tidak punya akses ke VPS. Tag `latest` hanya dipasang job `promote` setelah kelima image lolos tes dan Trivy. Deployer memegang `docker.sock` (setara root atas Docker), jadi: image resmi `docker` berversi terkunci, `network_mode: none`, berkas stack read-only. Perubahan berkas Compose atau rute Traefik tetap deploy manual. Belum ada rollback otomatis: jika API tidak sehat setelah deploy, deployer mencatat GAGAL di log (`docker logs pacetara-deployer`) dan perbaikan dilakukan dengan commit baru atau mengunci `IMAGE_TAG` ke tag lama di `.env`.

## Modul 1.4 Tracking lari (10 Nov 2026)

59. **Rekam di latar depan, bukan lokasi latar belakang.** `geolocator` dengan *foreground service* bertipe `location` (notifikasi "PaceTara sedang merekam lari") membuat rekaman tetap berjalan saat layar mati, tanpa `ACCESS_BACKGROUND_LOCATION` yang butuh deklarasi dan video di Play Console. Saat jeda, stream GPS tetap hidup (agar service tidak dimatikan sistem) tetapi titiknya diabaikan. Penghemat baterai agresif di beberapa merek HP (Xiaomi, Oppo, Vivo) masih bisa mematikan service; uji di HP sungguhan wajib.
60. **Statistik dihitung server dari titik GPS**, bukan dikirim aplikasi: titik yang waktunya mundur atau melompat > 12,5 m/s dibuang, jarak antar-segmen (jeda) tidak dihitung, waktu bergerak mengabaikan selisih > 30 detik. Aplikasi memakai aturan yang sama (`track.dart`) untuk tampilan langsung, plus membuang titik berakurasi > 25 m. Ini penting untuk liga dan papan peringkat Fase 2.
61. **Rute disimpan terenkripsi** (gzip JSON → `FieldCrypto`, AAD per lari) dalam dua versi: `route_full_enc` (hanya pemilik) dan `route_public_enc` (setelah zona privasi, untuk orang lain). PostGIS belum dipakai untuk rute; jika fitur spasial Fase 2 (peta spot, cari teman) butuh geometri, simpan geometri yang sudah dikaburkan/digeneralisasi, bukan rute mentah.
62. **Zona privasi:** semua titik dalam radius R dari titik awal DAN titik akhir disembunyikan dari orang lain, termasuk bagian tengah rute yang lewat dekat rumah lagi. R = `users.privacy_radius_m`, bawaan 250 m, bisa diubah pengguna (100 m–1 km) dan berlaku untuk lari berikutnya. Lari yang seluruhnya di dalam zona menghasilkan rute publik kosong. Statistik tetap utuh.
63. **Visibilitas lari:** `public` (semua pengguna Level 1), `community` (sesama anggota aktif satu komunitas; bawaan), `private` (hanya pemilik). Yang tidak berhak mendapat 404, seolah lari tidak ada. Lari yang diimpor dari Strava (modul 2.3) wajib `private` dan tidak boleh diubah.
64. **Upload idempoten dan aman offline:** aplikasi membuat `clientRunId` saat mulai merekam; lari yang selesai disimpan dulu di antrean di HP (`pending_runs/`, termasuk salinan foto), lalu diunggah. Upload ulang dengan `clientRunId` sama mengembalikan lari yang sudah ada. Rekaman yang sedang berjalan ditulis ke `current_run.json` setiap 10 titik, sehingga bisa dilanjutkan jika aplikasi dimatikan sistem.
65. **Batas riwayat paket gratis 90 hari** (`RUN_HISTORY_DAYS`): lari lebih lama disembunyikan dari pemiliknya (daftar dan detail), tidak dihapus. Respons setelah menyimpan tidak terkena batas ini, agar unggahan dari antrean lama tetap berhasil.
66. **Peta: `flutter_map`** dengan URL tile dari `--dart-define=MAP_TILE_URL`. Bawaan OpenStreetMap hanya untuk masa uji: kebijakan tile OSM melarang pemakaian berat oleh aplikasi. **Sebelum rilis publik, ganti ke penyedia tile berbayar** (mis. MapTiler, Stadia, atau Mapbox) dan perbarui kebijakan privasi. Penyedia peta menerima IP dan area yang dilihat, bukan rute atau akun.
67. **Belum diuji di HP sungguhan:** kriteria "5 km terekam utuh dengan layar mati" baru terbukti lewat simulasi (rute GPS buatan di tes Flutter dan e2e backend). Uji lapangan wajib sebelum modul ini dianggap selesai penuh: lari ≥ 5 km dengan layar mati, lalu periksa jarak, rute, dan zona privasi.

## Perbaikan setelah uji APK pertama (10 Nov 2026)

68. **Login Google satu kali pilih akun:** ID token dari pemilih akun pertama disimpan dan dikirim ulang setelah pengguna menyetujui kebijakan privasi (akun baru), bukan membuka pemilih akun lagi. ID token Google berlaku ±1 jam.
69. **Atribusi peta:** label "flutter_map" dihapus. Atribusi "© OpenStreetMap contributors" **wajib** menurut lisensi ODbL, jadi tetap ada: tampil 5 detik lalu mengecil menjadi ikon (i) yang bisa diketuk (tautan ke openstreetmap.org/copyright), sesuai pedoman atribusi OSM untuk layar kecil. Saat pindah ke penyedia tile lain, ikuti syarat atribusi penyedia itu.
70. **Karakter pelari di peta:** pilihan karakter dan warna (8 bawaan) disimpan lokal di HP (`shared_preferences`), tidak dikirim ke server. Arah panah dihitung dari titik ≥ 15 m ke belakang agar tidak berputar karena derau GPS. Saat belum merekam, posisi hanya ditampilkan jika izin lokasi sudah pernah diberikan (tidak memunculkan dialog izin).
71. **Pemeriksa pembaruan diperbaiki:** sebelumnya memakai `FutureProvider.autoDispose` yang dibaca dengan `ref.read(...future)` tanpa pendengar, sehingga bisa dibuang sebelum selesai dan dialog tidak pernah muncul. Sekarang fungsi biasa `checkForUpdate`, dipasang di kerangka beranda, dan dijalankan saat aplikasi dibuka serta setiap kembali dari latar belakang (maks. sekali per 15 menit). Pelajaran umum: jangan `ref.read(provider.future)` pada provider autoDispose tanpa pendengar.
72. **Profil menjadi tab keempat** di menu bawah (Lari, Riwayat, Komunitas, Profil); sebelumnya hanya foto kecil di kanan atas tab Komunitas dan mudah terlewat.

## Modul 1.5 Status lari (10 Nov 2026)

73. **Status lari hanya di Redis, tidak pernah di Postgres.** `live:s:<user>` (JSON status, TTL 180 detik) dan `live:c:<komunitas>` (sorted set pelari, skor = waktu kedaluwarsa). Aplikasi memperbarui lewat `PUT /v1/live` tiap 10 detik (idempoten per `clientRunId`, sehingga status pulih sendiri setelah Redis restart atau HP sempat offline). Dihapus eksplisit lewat `DELETE /v1/live` saat lari selesai/dibuang, otomatis saat lari diunggah (`POST /v1/runs` dengan `clientRunId` sama), dan saat hapus akun. Jika aplikasi mati tanpa sempat mengakhiri, status hilang sendiri setelah 3 menit.
74. **Hak akses dicek ulang di setiap permintaan**, bukan hanya saat mulai: `PUT` membuang komunitas yang bukan tempat pengguna terdaftar aktif, dan `GET /v1/communities/:id/live` hanya untuk anggota aktif serta menyaring pelari yang masih anggota aktif dengan akun aktif (keluar/diblokir = langsung hilang dari daftar).
75. **Posisi peta opsional per komunitas, pilihan pelari** (bukan pengaturan admin), bawaan tidak. Posisi dan titik awal hanya dikirim aplikasi jika minimal satu komunitas diizinkan melihat peta, dibulatkan server ke 4 desimal (±11 m), dan disimpan terenkripsi `FieldCrypto` (AAD `live.pos:<user>` / `live.origin:<user>`) walau hanya di Redis.
76. **Zona privasi berlaku juga untuk posisi langsung:** selama pelari berada dalam `privacy_radius_m` dari titik awal rekaman (dikirim aplikasi sebagai `origin`), posisinya tidak disimpan dan tidak ditampilkan ("posisi disembunyikan"). Ini juga menyembunyikan saat pelari kembali ke rumah jika lari berakhir di titik awal. Rumah yang bukan titik awal (lari dari tempat lain, pulang ke rumah) tidak bisa dideteksi saat lari berlangsung; pelari bisa mematikan posisi peta kapan saja.
77. **Pilihan berbagi tidak disimpan:** setiap lari baru mulai dengan status mati (PRD: "Bawaan: mati"), termasuk setelah draf rekaman dipulihkan. Dipilih lewat chip "Status lari" di layar Lari, bisa diubah saat merekam (mematikan = status langsung dihapus dari server).
78. **WebSocket memakai pustaka `ws` langsung** (bukan `@nestjs/websockets`), dipasang di event `upgrade` server HTTP Nest pada `wss://<api>/v1/ws`. Alasannya: kontrol penuh atas handshake (token di header `Authorization`, bukan URL; tolak tanpa HTTPS di produksi; batas 30 handshake/menit per IP; maks. 5 koneksi per pengguna; Level 1 wajib). Koneksi ditutup kode 4001 saat token akses kedaluwarsa, sehingga sesi yang dicabut terputus paling lambat 15 menit. Fan-out lewat Redis pub/sub (`rt:<kanal>`) agar siap untuk >1 replika API. Traefik dan Caddy meneruskan WebSocket tanpa konfigurasi tambahan.
79. **Pesan WebSocket hanya sinyal, bukan data** (`{"op":"event","ch":"community:<id>:live","ev":"live.changed"}`). Aplikasi lalu memuat data lewat REST yang diperiksa hak aksesnya, jadi otorisasi data hanya ada di satu tempat. Setiap kanal wajib punya authorizer di server (`RealtimeService.register`); kanal tanpa authorizer selalu ditolak. Modul chat (1.6) memakai hub yang sama; untuk chat, pertimbangkan mengirim isi pesan langsung lewat WebSocket dengan pemeriksaan keanggotaan ulang berkala, karena pola sinyal + muat ulang boros untuk percakapan ramai.
80. **Aplikasi:** `RealtimeClient` memakai `WebSocket.connect` dengan `HttpClient` ber-pinning yang sama dengan Dio, tersambung hanya selama ada kanal yang didengarkan, jeda sambung ulang 1→30 detik, dan memancarkan `reconnected` agar daftar dimuat ulang. Daftar "sedang lari" juga polling 30 detik sebagai cadangan. Durasi di daftar berdetak di HP di antara pembaruan (maks. 60 detik ekstrapolasi); pembaruan > 45 detik ditandai "sinyal terakhir … lalu".
81. **Belum diuji di dua HP sungguhan:** kriteria "status muncul dalam beberapa detik" terbukti di tes e2e (sinyal WebSocket < 3 detik setelah `PUT`), dan "tidak terlihat orang luar" diuji untuk bukan anggota, komunitas yang tidak dipilih, dan anggota yang keluar. Uji lapangan: dua HP, satu merekam dengan status menyala (layar mati), satu membuka halaman komunitas.

## Modul 1.6 Chat (10 Nov 2026)

82. **Skema:** `conversations` (`direct` = satu baris per pasangan pengguna terurut `user_a < user_b`; `community` = satu per komunitas, dibuat saat pertama dibuka), `chat_messages` dengan `seq` identity global sebagai kursor paging/sinkronisasi, `chat_reads` (jumlah belum dibaca), `chat_run_invite_rsvps`. Isi teks dan JSON ajakan lari dienkripsi `FieldCrypto` (AAD `chat_messages.body:<id>`); karena itu tidak ada pencarian pesan di server (REVIEW-PRD D3).
83. **Hak akses dicek di setiap permintaan:** chat pribadi hanya kedua pesertanya; chat komunitas hanya anggota aktif. Yang tidak berhak mendapat 404 (percakapan, pesan, gambar, tandai dibaca, kanal WebSocket). Anggota yang keluar/dikeluarkan langsung kehilangan akses.
84. **Riwayat anggota baru:** kolom `community_members.history_from` (NULL = seluruh riwayat). Bergabung ke komunitas terbuka atau lewat kode undangan mengikuti `new_members_see_history` (bawaan tidak). Persetujuan admin (komunitas privat) memakai pilihan admin di dialog persetujuan (`seeHistory`), bawaannya pengaturan komunitas. Anggota yang sudah ada sebelum modul ini dan pemilik melihat seluruh riwayat.
85. **Chat pribadi hanya dengan sesama anggota aktif satu komunitas** (anti-spam, sejalan dengan #52), berlaku untuk memulai dan mengirim. Riwayat lama tetap bisa dibaca setelah tidak lagi satu komunitas. Fitur blokir pengguna belum ada; ditambahkan bersama laporan (1.8) bila dibutuhkan.
86. **Kirim idempoten:** aplikasi membuat `clientMsgId` (UUID v4) per pesan; unik per (pengirim, clientMsgId), jadi kirim ulang setelah sinyal putus tidak membuat pesan ganda. Pesan gagal tampil "Gagal terkirim · ketuk untuk kirim ulang". Belum ada antrean kirim offline yang bertahan setelah aplikasi ditutup.
87. **Hapus pesan sendiri = tombstone:** `deleted_at` diisi, isi (`body_enc`) dan gambar dihapus saat itu juga, RSVP dihapus; constraint `chat_deleted_is_empty` memastikan tidak ada isi tersisa. Pesan dengan `held_at` (diisi modul 1.8 saat dilaporkan) tidak bisa dihapus (409 `message_held`) agar bukti tidak hilang sebelum ditinjau.
88. **Gambar chat:** diproses seperti foto lain (cek isi, maks 8 MB, WebP 1600 px, EXIF/GPS terbuang), disimpan di `chat/<percakapan>/<pesan>.webp`, diambil lewat `/v1/chat/messages/:id/image` dengan token. Worker menjalankan `chat-image-expiry` tiap jam: gambar > 180 hari dihapus dari penyimpanan, pesan tetap dengan `image_expired_at` → "Gambar sudah kedaluwarsa". Menghapus komunitas ikut menghapus gambar chat-nya dari penyimpanan (dikumpulkan sebelum `ON DELETE CASCADE`).
89. **Hapus akun:** pesan pengguna di chat pribadi dihapus (beserta gambarnya); pesan lawan bicara tetap untuk lawan bicara, dan ia tidak bisa membalas ke akun terhapus. Di chat komunitas pesan tetap dan nama otomatis "Pengguna dihapus" karena `display_name` dianonimkan.
90. **Realtime:** kanal `conv:<id>` (event `message.new {seq}`, `message.updated {id}`) dan `user:<id>:chat` (`inbox.changed`, chat pribadi baru). Tetap pola sinyal + muat lewat REST (#79): untuk skala sekarang satu GET kecil per pesan per penonton masih murah, dan otorisasi data tetap di satu tempat. Daftar percakapan berlangganan maks. 40 kanal percakapan (batas server 50 per koneksi). Cadangan polling: ruang chat 30 detik, daftar 60 detik.
91. **Kartu "bagikan event" ditunda ke modul 1.7** karena belum ada data event. Kartu ajakan lari bareng sudah ada (judul, waktu ≤ 90 hari ke depan, tempat, catatan, tombol Ikut/Batal ikut, daftar nama yang ikut maks. 10).
92. **Batas laju per pengguna untuk permintaan ber-login** (`UserThrottlerGuard`): tracker = id pengguna jika token akses sah, selain itu IP. Alasannya: pengguna seluler Indonesia banyak di balik CGNAT, sehingga batas per IP (mis. kirim chat 30/menit, gambar 10/menit) akan menolak banyak orang sekaligus. Endpoint tanpa login (login, daftar, OTP, refresh) tetap per IP, dan Traefik tetap membatasi per IP di depan. Ini juga mengubah batas yang sudah ada (unggah lari, status lari, pakai kode undangan) menjadi per pengguna; untuk kode undangan tetap aman karena akun wajib Level 1 (nomor HP terverifikasi).

## Modul 1.8 Laporan konten dan panel super admin (10 Nov 2026)

93. **Laporan** (`reports`): sasaran `user`, `community`, `message` (`event` disiapkan untuk 1.7). Alasan tetap (spam, pelecehan, kebencian, seksual, kekerasan, penipuan, menyamar, lainnya) + keterangan opsional terenkripsi. Pelapor hanya bisa melaporkan yang bisa ia lihat (pesan di percakapannya, komunitas yang ada, pengguna yang satu komunitas atau pernah chat pribadi); selain itu 404, agar endpoint tidak dipakai menebak id. Satu laporan terbuka per pelapor per sasaran. Batas 20 laporan/jam per pengguna.
94. **Ditahan dan disembunyikan otomatis:** pesan yang dilaporkan langsung `held_at` (pengirim tidak bisa menghapusnya, #87). Setelah **3 pelapor berbeda** (`AUTO_HIDE_REPORTERS`), pesan `hidden_at` (orang lain melihat "Pesan disembunyikan sambil ditinjau", pengirim tetap melihat isinya) dan komunitas `hidden_at` (hilang dari direktori dan daftar kota, anggota tetap bisa membuka). Pengguna tidak disembunyikan otomatis; tindakan akun selalu manual. Angka 3 belum diputuskan pemilik; ubah di `reports.service.ts`.
95. **Login panel = kata sandi + TOTP** (RFC 6238, SHA1/30 detik/6 digit, toleransi ±1 langkah, ditulis sendiri tanpa dependensi, diuji dengan vektor RFC). Rahasia TOTP terenkripsi `FieldCrypto` (AAD `users.totp:<id>`). Kode tidak bisa dipakai ulang (Redis `SET NX` per langkah). Semua kegagalan memberi pesan sama; 5 kali gagal → akun panel terkunci 15 menit; batas 5 percobaan/menit per IP.
96. **Token panel terpisah dari token aplikasi:** hanya login panel yang menghasilkan token bertanda `adm` (klaim JWT) dan `refresh_tokens.admin_session`. Rotasi mempertahankan tanda itu, dan sesi panel berakhir paling lambat **12 jam** sejak login (tidak diperpanjang saat rotasi). `AdminGuard` mewajibkan `adm` + peran `super_admin` + akun aktif (dicek ke database setiap permintaan). Akibatnya, token aplikasi HP milik super admin tidak bisa membuka `/v1/admin`.
97. **Super admin hanya dibuat lewat CLI di server** (`node dist/scripts/admin.js promote|reset-totp|demote <email>`), tidak ada pendaftaran 2FA lewat web (yang memungkinkan siapa pun yang tahu kata sandi mendaftarkan authenticator-nya sendiri lebih dulu). Akun wajib punya kata sandi. Perintah CLI tercatat di log dengan pelaku kosong ("CLI").
98. **Panel web:** token akses hanya di memori; token penyegar di `sessionStorage` (hilang saat tab ditutup). Risiko XSS ditekan CSP ketat (`script-src 'self'`, tanpa style inline). Isi pesan tidak tampil di antrean; hanya di detail laporan, beserta 10 pesan sebelum dan sesudahnya, dan setiap pembukaan tercatat (`report.view_message`). Pesan tanpa laporan tidak bisa dibuka sama sekali (PRD: "Super admin hanya bisa membuka chat yang dilaporkan").
99. **Tindakan:** abaikan (laporan `dismissed`, tahanan/penyembunyian dicabut) atau turunkan (laporan `actioned`; pesan menjadi tombstone `removed_by_admin` dan gambarnya dihapus; komunitas `removed_at` = dianggap tidak ada bagi semua orang termasuk anggota, chat-nya ikut tertutup, hanya pemilik yang masih bisa menghapusnya). Akun: tangguhkan (1/7/30 hari atau tanpa batas), blokir, pulihkan, semuanya wajib alasan; sesi langsung dicabut dan status lari dihapus. Super admin dan diri sendiri tidak bisa ditindak dari panel. Cari akun hanya dengan email lengkap (blind index, lewat body), email tidak dicatat di log.
100. **Penangguhan berbatas waktu dipulihkan otomatis saat login** setelah `suspended_until` lewat (tanpa job terjadwal). Login akun ditangguhkan/diblokir mendapat `account_suspended`/`account_banned` dengan `appealable: true`; aplikasi menawarkan banding.
101. **Banding akun:** `POST /v1/auth/appeal` tanpa login, dengan kredensial yang sama seperti login (email + kata sandi, atau ID token Google) karena akun tidak bisa login. Satu banding terbuka per akun, isi terenkripsi, batas 5/jam per IP. Diterima → akun dipulihkan. Banding atas penurunan konten (bukan akun) belum ada.
102. **Log tindakan** `admin_audit_log` mencatat login/gagal/terkunci, setiap pembukaan detail laporan pesan dan profil pengguna, pencarian, setiap tindakan beserta alasan, dan keputusan banding. Tabel hanya bisa ditambah (trigger dari modul 1.1). Hapus akun: keterangan laporan yang ditulis pengguna dihapus dan bandingnya dihapus; catatan laporan dan log tetap.

## WAF CrowdSec di VPS bersama (11 Nov 2026)

103. **CrowdSec AppSec (OWASP CRS) di VPS menolak PATCH/PUT/DELETE** lewat rule 911100 ("Method is not allowed by policy"; CRS bawaan hanya GET/HEAD/POST/OPTIONS), dengan 403 tanpa body sebelum permintaan sampai ke API. Akibatnya simpan profil, status lari, ubah/hapus lari, hapus pesan, batal ikut ajakan, dan ubah pengaturan komunitas gagal di produksi, walau semua tes lolos (tes tidak melewati WAF). Perbaikan: pengecualian sempit `infra/crowdsec/pacetara-api-exclusions.yaml` (pola sama dengan `keycloak-admin-exclusions.yaml` milik infra) yang melepas HANYA 911100, HANYA host `pace-api.bimacreative.tech`, path `/v1/`, metode PATCH/PUT/DELETE; rule CRS lain tetap aktif. Tidak memakai method override (POST + header) agar aturan keamanan tidak diakali diam-diam. Aplikasi kini menampilkan kode HTTP untuk penolakan tanpa JSON ("Permintaan ditolak server (HTTP 403)").
    - **Pasang (manual, di VPS):** salin berkas ke `/opt/infra/security/crowdsec/appsec-configs/`, tambahkan `- local/pacetara-api-exclusions` di `acquis.d/appsec.yaml` (di bawah entri keycloak), tambahkan mount-nya di docker-compose CrowdSec meniru baris `keycloak-admin-exclusions.yaml`, lalu recreate container CrowdSec (fail-closed ±50 detik: semua situs di VPS bisa 403 selama itu).
    - **Risiko yang perlu dipantau:** rule CRS lain bisa salah tangkap isi bebas dari pengguna, terutama teks chat, catatan lari, dan deskripsi komunitas (mis. kalimat mirip SQL → 942xxx, `${...}` → 932130). Gejalanya 403 "Permintaan ditolak server" saat mengirim teks tertentu. Jika terjadi, tambahkan pengecualian sempit per rule dan per path dengan pola yang sama, jangan mematikan CRS untuk seluruh host.


## Modul 1.7 Kalender event manual (11 Nov 2026)

104. **Skema:** `events` (nama, `event_date` bertipe `date` = tanggal setempat penyelenggara, `start_time` opsional, kota, lokasi, deskripsi, `categories` dari himpunan tetap `fun`/`5k`/`10k`/`hm`/`fm`/`ultra`/`other`, `registration_url` wajib `https://`) dan `event_participants` (tanda "ikut"). Nama + tanggal unik (tanpa beda huruf besar/kecil) agar event tidak dimasukkan dua kali (`409 event_exists`). Tanggal dikirim sebagai teks `YYYY-MM-DD` (`to_char`), bukan `Date` JavaScript, agar tidak bergeser zona waktu.
105. **Input hanya oleh super admin** lewat tab Event di panel (`/v1/admin/events`, `AdminGuard` = token login panel + TOTP). Buat, ubah, dan hapus tercatat di `admin_audit_log` (`event.create|update|delete`, metadata hanya nama + tanggal). Panel memakai `PUT`/`DELETE` (sudah lolos WAF lewat pengecualian #103). Tanggal lampau ditolak saat membuat, tetapi boleh saat mengubah (untuk memperbaiki salah ketik event lama). Hapus = hapus permanen (untuk salah input); untuk konten bermasalah pakai alur laporan (turunkan = `removed_at`).
106. **Arsip otomatis:** job worker `event-archive` tiap jam mengisi `archived_at` untuk event dengan `event_date` < hari ini **WIB** (`Asia/Jakarta`). Daftar juga menyaring `event_date >= hari ini WIB`, jadi jeda sampai job berikutnya tidak terlihat. Event di WITA/WIT jadi diarsipkan 1–2 jam setelah tengah malam setempat; dianggap cukup. Event arsip tidak tampil di daftar, detailnya tetap bisa dibuka (mis. dari kartu chat), dan tidak bisa ditandai ikut (`409 event_archived`). Tanda ikut tidak dihapus saat arsip (bahan paspor lari 2.2). Mengubah tanggal ke masa depan membatalkan arsip.
107. **"Siapa ikut?" dan privasi:** jumlah total peserta terlihat semua pengguna Level 1; nama hanya untuk **sesama anggota aktif satu komunitas** (komunitas yang tidak diturunkan), beserta maks. 3 nama komunitas bersama. Sama dengan aturan profil #52: keluar/dikeluarkan dari komunitas = nama langsung hilang. Aplikasi menulis "Anggota komunitasmu bisa melihat bahwa kamu ikut" di bawah tombol, dan kebijakan privasi (bagian 4 dan 9) ditambah satu butir. **Versi kebijakan tidak dinaikkan** (`PRIVACY_POLICY_VERSION` tetap `2026-11-10`) karena ini penjelasan fitur, bukan perubahan dasar pemrosesan; pemilik bisa menaikkannya jika ingin semua pengguna menyetujui ulang.
108. **Filter:** kota (sama persis, tanpa beda huruf besar/kecil, seperti direktori komunitas), bulan (`YYYY-MM`), dan `going=true` ("yang saya ikuti"). Paging dengan kursor `(event_date, id)`. Kota dan bulan boleh di query string karena bukan data pribadi. Daftar dibatasi 60/menit per pengguna; ikut/batal 30/menit.
109. **Kartu "bagikan event" di chat** (menyusul #91): jenis pesan `event`, isi terenkripsi `{eventId, name}`. Nama disimpan untuk pratinjau daftar percakapan dan sebagai cadangan; kartu selalu menampilkan data terkini dari tabel `events` (nama, tanggal, kota, kategori, arsip). Event yang dihapus/diturunkan tampil "Event tidak tersedia lagi" (`available: false`). Berbagi hanya event yang ada (selain itu 404). Di aplikasi: tombol bagikan di detail event → pilih percakapan → kirim → buka chat.
110. **Laporan event:** sasaran `event` aktif di `POST /v1/reports` (semua pengguna Level 1 boleh, karena event terlihat semua orang). 3 pelapor → `hidden_at` (hilang dari daftar, detail tetap bisa dibuka); turunkan → `removed_at` (404 bagi semua, kartu chat "tidak tersedia"); abaikan → `hidden_at` dicabut.
111. **Aplikasi:** pintu masuk lewat kartu "Kalender event lari" dan ikon kalender di tab Komunitas (bukan tab keenam, karena menu bawah sudah lima). Tautan pendaftaran dibuka di browser luar (`LaunchMode.externalApplication`) setelah aplikasi memeriksa ulang skemanya `https`; ditegaskan bahwa pendaftaran dan pembayaran terjadi di situs penyelenggara. Hapus akun menghapus semua tanda ikut.
112. **Tes lokal di Windows:** jalankan vitest dari PowerShell dengan path huruf drive besar (`E:\...`). Dari Git Bash dengan cwd `e:\...` (huruf kecil), vitest memuat modulnya dua kali dan semua suite gagal dengan "Cannot read properties of undefined (reading 'config')". Tes Flutter bisa dijalankan tanpa memasang Flutter: `docker run --rm -v "<repo>/mobile:/app" -w /app ghcr.io/cirruslabs/flutter:stable sh -c "flutter pub get && flutter analyze && flutter test"`.

## Modul 1.9 Notifikasi (11 Nov 2026)

113. **Dua jalur:** kotak notifikasi di aplikasi (tabel `notifications`, ikon lonceng di tab Komunitas, sinyal WebSocket `user:<id>:notif`) yang selalu berjalan, dan push **Firebase Cloud Messaging HTTP v1** yang aktif hanya jika dikonfigurasi. Push dikirim **worker** lewat antrean BullMQ `notifications` (job `push`, 3 percobaan, backoff eksponensial), bukan oleh API, agar permintaan pengguna tidak menunggu Google. Kegagalan notifikasi tidak pernah menggagalkan permintaan asal.
114. **Isi push minimal:** judul dan teks hanya memuat nama pengirim/komunitas dan jenis aksi ("Ani mengirim pesan", "Budi mengajak lari bareng"), plus id untuk navigasi. **Isi chat, judul ajakan lari, dan lokasi tidak pernah dikirim ke Google**, karena isi chat dijanjikan terenkripsi di perjalanan dan di database. Kotak notifikasi hanya menyimpan id (pelaku, komunitas, percakapan); nama dibaca saat ditampilkan, sehingga akun terhapus tampil "Pengguna dihapus".
115. **Jenis dan pengaturan:** empat kategori sesuai PRD: `chat` (pesan baru, push saja, satu notifikasi per percakapan lewat `tag`), `community` (undangan langsung, permintaan bergabung ke admin, permintaan diterima; push + kotak), `run_invite` (ajakan lari di chat; push + kotak), `friend_running` (anggota komunitas mulai lari; push saja, sekali per lari per komunitas lewat Redis `SET NX` 6 jam, hanya ke komunitas yang dipilih pelari, sama dengan siapa yang boleh melihat statusnya). Pengaturan (`notification_prefs.disabled`, bawaan semua menyala) mengatur push; kotak notifikasi tetap mencatat agar undangan tidak hilang.
116. **Token perangkat:** `push_tokens` terikat ke **sesi login** (family token penyegar). Logout dan pencabutan sesi (`revokeFamily`, `revokeAllForUser`, termasuk penangguhan akun) menghapus tokennya, jadi perangkat yang keluar tidak menerima push. Token terenkripsi `FieldCrypto` dengan SHA-256 untuk keunikan; token yang pindah akun (HP sama, akun lain) ikut berpindah. Token yang ditolak FCM (`UNREGISTERED`/404) dihapus worker. Token tidak pernah di-log.
117. **Konfigurasi:** server memakai `FCM_SERVICE_ACCOUNT_B64` (JSON akun layanan Firebase, base64) di `.env`; aplikasi memakai `--dart-define` `FIREBASE_API_KEY`/`APP_ID`/`SENDER_ID`/`PROJECT_ID` dari **variabel repo GitHub** (Settings → Variables, bukan Secrets karena nilai ini memang ikut di APK). Firebase diinisialisasi dengan `FirebaseOptions` langsung, tanpa `google-services.json` dan plugin Gradle `google-services`. Selama variabel kosong, APK tetap jalan tanpa push. **Pemilik perlu membuat proyek Firebase** (bisa memakai proyek Google Cloud yang sama dengan login Google), mendaftarkan aplikasi Android `tech.bimacreative.pacetara`, lalu mengisi kedua sisi.
118. **firebase_messaging 17** menandai `getToken`/`onTokenRefresh` usang dan menggantinya dengan `register()`/`onRegistered` yang memberi Firebase Installation ID. Kami tetap memakai token registrasi (diberi `ignore` beralasan) karena server mengirim ke field `token` FCM HTTP v1; pindah ke FID setelah pengiriman ke FID terbukti didukung API v1. Push di latar depan tidak ditampilkan sistem; aplikasi hanya menyegarkan lonceng. Notifikasi memakai kanal bawaan FCM dan ikon aplikasi; kanal dan ikon notifikasi khusus menyusul (perlu `flutter_local_notifications` atau sumber daya drawable).
119. **Undangan komunitas langsung** (menutup #51): admin hanya bisa mengundang pengguna yang **sudah ia kenal**: sesama anggota aktif komunitas lain (yang tidak diturunkan) atau pernah chat pribadi. Tidak ada pencarian pengguna bebas. Daftar kandidat di `GET /v1/communities/:id/invite-candidates`. Undangan berlaku 30 hari, satu yang menunggu per pengguna per komunitas. Menerima undangan langsung menjadikan anggota aktif (undangan menggantikan persetujuan admin di komunitas privat) dengan batas paket tetap ditegakkan saat menerima; riwayat chat mengikuti pengaturan komunitas. Pengguna yang diblokir dari komunitas tidak bisa diundang (`409 user_banned`).
120. **Tes:** antrean push diganti `FakePushQueue` di tes e2e; pengirim FCM diuji lewat `sendPushJob` dengan pengirim palsu. Pengiriman sungguhan ke HP belum diuji karena proyek Firebase belum ada.

## Modul 1.10 Mode aman (11 Nov 2026)

121. **Gratis untuk semua pengguna Level 1** (REVIEW-PRD A1: fitur keselamatan tidak di balik paywall), walau tabel Gratis vs berbayar di PRD masih menulis Premium.
122. **Kontak darurat:** maks. 3 per pengguna, nama + nomor terenkripsi `FieldCrypto` (data pihak ketiga), blind index hanya untuk mencegah duplikat. Nomor dinormalisasi ke `+62…` (`normalizePhoneId`). Kontak tidak diberi tahu saat ditambahkan (menghindari pesan WhatsApp tak diminta dan penyalahgunaan nomor pengirim); aplikasi meminta pengguna memberi tahu kontaknya sendiri.
123. **Dua jalur SOS:** (1) server mengirim WhatsApp ke semua kontak lewat wa-otp `POST /sos` (lokasi sebagai tautan Google Maps, jam WIB, akurasi); (2) aplikasi **selalu** menawarkan SMS dari HP pengguna ke semua kontak sekaligus (`sms:` URI) dan tombol telepon 112. SMS berfungsi tanpa internet; untuk itu daftar kontak disalin di Android Keystore (`flutter_secure_storage`) dan dihapus saat keluar/hapus akun. Baileys bisa diblokir (risiko yang sudah diketahui), jadi WhatsApp server tidak boleh menjadi satu-satunya jalur.
124. **Teks SOS disusun di wa-otp**, bukan dari API: endpoint hanya menerima data terstruktur (nomor, nama, lat/lng, akurasi, waktu) yang divalidasi, dan nama dibersihkan dari karakter format WhatsApp/baris baru. Endpoint ini tidak bisa dipakai mengirim teks bebas lewat nomor WhatsApp PaceTara.
125. **Mencegah salah pencet dan penyalahgunaan:** tombol SOS hanya tampil saat merekam/dijeda, dengan hitung mundur 5 detik yang bisa dibatalkan (atau "Kirim sekarang"). Batas server: 3 SOS per 10 menit dan 10 per hari per pengguna; jika terkena, server menjawab `429 sos_rate_limited` beserta daftar kontak agar aplikasi tetap bisa mengirim SMS. Throttler HTTP 10/10 menit hanya penahan kasar.
126. **Privasi lokasi:** lokasi dikirim di body, **tidak disimpan** di database dan tidak di-log. `sos_alerts` hanya mencatat waktu, jumlah kontak, dan jumlah terkirim (untuk batas laju dan audit). Lokasi diambil dari titik rekaman terakhir jika < 30 detik, selain itu GPS saat ini (batas 10 detik), lalu posisi terakhir yang diketahui. Zona privasi tidak berlaku untuk SOS (tujuannya justru memberi lokasi tepat ke orang yang dipilih pengguna).
127. **Belum diuji di HP sungguhan:** pengiriman WhatsApp SOS ke nomor nyata, pembukaan aplikasi SMS dengan banyak penerima (perilaku berbeda antar merek HP), dan GPS saat layar mati perlu uji lapangan.

## Modul 2.1 Feed sosial (11 Nov 2026)

134. **Skema:** `feed_posts` (jenis `text`/`photo`/`run`, teks opsional, visibilitas, `run_id` opsional, `held_at`/`hidden_at`/`removed_at` seperti chat dan event), `feed_post_photos` (maks. 4, posisi 0–3), `feed_comments`, `feed_likes`, `feed_follows` (satu arah, tanpa persetujuan), `feed_blocks`. Jumlah suka dan komentar dihitung saat dibaca (bukan kolom penghitung) agar akun nonaktif, komentar tersembunyi, dan blokir langsung tercermin tanpa sinkronisasi. Tidak ada fitur ubah postingan; penulis menghapus lalu memposting ulang.
135. **Teks postingan dan komentar dienkripsi `FieldCrypto`** (AAD `feed_posts.body:<id>` / `feed_comments.body:<id>`), walau CLAUDE.md hanya mewajibkan HP, email, rute, dan chat. Alasannya: postingan komunitas/pengikut bersifat semi-privat dan bisa berisi data pribadi (jadwal, lokasi kumpul), feed tidak butuh pencarian teks di server, dan biayanya kecil (pola yang sama dengan chat). Konsekuensi: tidak ada pencarian isi feed di server, dan moderasi membaca isi lewat panel (tercatat di log).
136. **Visibilitas postingan:** `public` (semua pengguna Level 1, satu-satunya yang masuk Jelajah), `community` (sesama anggota aktif satu komunitas yang tidak diturunkan, sama dengan lari #63, bukan satu komunitas tertentu), `followers` (pengikut). Aturan baca ada di satu tempat (`VISIBLE` di `feed.service.ts`) dan dipakai detail, tiga tab, komentar, suka, foto, dan laporan; yang tidak berhak mendapat 404. Tab: **Mengikuti** = diri sendiri + yang diikuti, **Komunitas** = diri sendiri + sesama anggota komunitas, **Jelajah** = publik yang tidak disembunyikan. Paging kursor `(created_at, id)` memakai timestamp teks Postgres (presisi mikrodetik, tidak terpotong ke milidetik seperti `Date` JavaScript).
137. **Postingan hasil lari:** hanya lari milik sendiri, bukan `private`, bukan sumber `strava` (PRD 2.3); selain itu `409 run_not_shareable`. Postingan tidak boleh lebih luas dari larinya: lari `community` hanya bisa jadi postingan `community` (`400 visibility_too_wide`). Satu lari hanya bisa diposting sekali (`409 run_already_posted`). Saat dibaca, kartu lari diperiksa ulang dengan aturan lari (`RunsService.feedCards`): jika lari kemudian dijadikan privat, dihapus (`ON DELETE SET NULL`), atau penonton tidak berhak, postingan tetap tampil tetapi kartu lari "tidak tersedia" (`runUnavailable`). Rute di feed **selalu rute publik** (setelah zona privasi), juga bagi pemiliknya, diringkas maks. 150 titik dan digambar sebagai sketsa tanpa peta (tanpa permintaan tile).
138. **Profil feed dan foto profil:** profil pengguna lain (`GET /v1/feed/users/:id`) terlihat jika satu komunitas, salah satu mengikuti yang lain, atau ia aktif di feed publik (punya postingan publik atau komentar di postingan publik), dan tidak ada blokir. Ini memperluas #52 untuk foto profil (`/v1/users/:id/avatar`) dengan aturan yang sama, karena penulis postingan publik perlu tampil dengan fotonya. Profil feed hanya berisi nama, foto, lencana verifikasi, dan jumlah pengikut/diikuti; kota dan pace tetap hanya untuk sesama anggota komunitas. **Daftar pengikut dan yang diikuti hanya untuk pemiliknya** (jejaring sosial tidak dibuka ke orang lain). Penulis komentar di postingan komunitas terlihat namanya oleh penonton postingan itu walau profilnya tidak bisa dibuka; ini konsekuensi berkomentar di postingan orang lain.
139. **Blokir pengguna khusus feed** (menutup sebagian #85): kedua arah tidak saling melihat postingan, komentar, dan profil feed; follow kedua arah diputus dan tidak bisa dibuat lagi. Bisa memblokir pengguna mana pun yang ada (mis. penulis komentar yang profilnya tidak terlihat). Blokir **tidak** memengaruhi chat dan komunitas; perluasan ke chat pribadi bisa diputuskan nanti. "Hapus pengikut" memutus follow tanpa memblokir. Akun ditangguhkan/diblokir super admin: semua kontennya (postingan, komentar, suka dalam hitungan) tidak tampil selama status bukan `active`, dan kembali saat dipulihkan.
140. **Laporan feed:** sasaran `post` dan `comment` di `POST /v1/reports`, hanya untuk konten yang bisa dilihat pelapor (selain itu 404) dan bukan milik sendiri. Dilaporkan → `held_at` (penulis tidak bisa menghapus: `409 content_held`, seperti #87). 3 pelapor → `hidden_at` (hilang dari semua tab dan 404 bagi orang lain; penulis tetap melihat dengan tanda "disembunyikan sambil ditinjau"). Turunkan → `removed_at`, teks dihapus (constraint `*_removed_is_empty`) dan foto dihapus dari penyimpanan; abaikan → tahanan dan penyembunyian dicabut. Pengguna juga bisa dilaporkan dari profil feed (`canSeeProfile` ditambahkan ke syarat laporan pengguna). Panel admin menampilkan teks, hasil lari, dan foto postingan yang dilaporkan; foto diambil lewat `/v1/admin/feed/posts/:id/photos/:photoId` (hanya untuk postingan yang punya laporan) dengan token panel. Membuka detail postingan/komentar/foto tercatat (`report.view_post`, `report.view_comment`, `report.view_post_photo`).
141. **Foto postingan:** dikirim dalam satu permintaan multipart (`data` = JSON, `photos` maks. 4, masing-masing ≤ 8 MB; `fields: 1, fieldSize: 16 KB, parts: 5`), diproses `processImage` (cek isi, WebP 1600 px, EXIF/GPS terbuang) **sebelum** apa pun disimpan, di `feed/<pengguna>/<postingan>/<acak>.webp`, diambil lewat `/v1/feed/posts/:id/photos/:photoId` dengan token dan pemeriksaan `VISIBLE`. Aplikasi memperkecil foto ke maks. 2048 px (kualitas 85) sebelum unggah agar 4 foto muat di batas body Traefik 15 MB (#131). Postingan teks/hasil lari dikirim sebagai JSON biasa.
142. **Batas laju (per pengguna, #92):** buat postingan 10/menit + **30/hari** (Redis, `429 post_rate_limited`), komentar 20/menit, suka/batal 60/menit, ikuti/blokir 30/menit, daftar 60/menit, foto 300/menit (satu layar feed memuat banyak foto). Feed gratis untuk semua (PRD: "Tracking, status lari, chat, feed: Ya"), jadi tidak ada batas paket; angka 30/hari ada di `POSTS_PER_DAY`.
143. **Notifikasi:** kategori pengaturan baru `social` (pengikut baru, suka, komentar; push + kotak notifikasi `new_follower`/`post_like`/`post_comment`). Mengikuti pola #114: teks push hanya "Ani mengomentari postinganmu"; **isi komentar dan postingan tidak pernah dikirim ke Google**. Notifikasi suka dan pengikut baru maks. sekali per pasangan per 24 jam (Redis `SET NX`), agar suka-batal-suka atau ikuti-berhenti tidak membanjiri.
144. **Hapus akun:** postingan beserta foto (dihapus dari penyimpanan), komentar dan suka di postingannya, komentar dan suka pengguna di postingan orang lain, follow kedua arah, dan blokir kedua arah dihapus. Langkah feed dijalankan sebelum langkah lari. Catatan laporan tetap (#102); sasaran yang sudah terhapus tampil "(tidak ditemukan)" di antrean. Kebijakan privasi (bagian 2, 4, 9) ditambah butir feed; versi tidak dinaikkan (sama dengan #107).
145. **Kartu Instagram Story dibuat di HP:** gambar PNG 1080×1920 digambar dengan `dart:ui` (gradien, logo komunitas pilihan pengguna atau tanpa komunitas, sketsa **rute publik**, jarak, waktu, pace, judul, tanggal), disimpan sementara di folder cache, dibagikan lewat share sheet Android (`share_plus` 13, `ShareParams(files: …)`), lalu berkasnya dihapus. Tidak ada yang diunggah ke server. Hanya untuk lari milik sendiri (tombol bagikan di detail lari: "Bagikan ke feed" atau "Kartu untuk Instagram Story"). Instagram tidak punya jalur Story resmi untuk Android tanpa SDK Facebook, jadi pengguna memilih Instagram → Story dari share sheet.

Riwayat lari pindah ke ikon jam di tab Lari dan menu Profil (`/runs`); antrean unggah lari kini dicoba saat beranda dibuka (sebelumnya dipicu tab Riwayat). Modul 2.2 (Riwayat dan paspor lari) bisa meninjau ulang penempatan ini.
147. **Belum diuji di HP sungguhan:** share sheet ke Instagram Story (perilaku antar versi Instagram), unggah 4 foto lewat jaringan seluler, dan tampilan kartu dengan logo komunitas. Realtime feed tidak dibuat (tidak wajib); daftar dimuat ulang dengan tarik-ke-bawah.

## Modul 2.2 Riwayat dan paspor lari (11 Nov 2026)

148. **Statistik dihitung server** (`GET /v1/runs/mine/stats?period=week|month|year&count=`): deret periode lengkap (periode kosong tetap muncul) dengan jumlah lari, jarak, waktu bergerak, dan pace rata-rata (waktu bergerak ÷ jarak). Agregasi di Postgres dengan `AT TIME ZONE 'Asia/Jakarta'` dan `date_trunc` (minggu mulai **Senin**). Semua lari pemilik dihitung, termasuk lari privat dan impor Strava, karena ini riwayat pribadinya (PRD 2.3 hanya melarang Strava di feed, papan peringkat, dan statistik komunitas). Bawaan 12 minggu / 6 bulan / 5 tahun; maks. 52 / 24 / 10.
149. **"Statistik lengkap" Premium** (`hasFullStats` di `plans.ts`): rentang tahunan, rentang minggu/bulan sampai batas maksimal, total sepanjang masa, dan rekor pribadi (5K/10K/HM/FM). Paket gratis: minggu/bulan dipotong ke periode yang memuat awal jendela 90 hari (#65), lari di luar jendela tidak dihitung, total hanya 90 hari; `period=year` → `403 limit_reached` dengan `limit.kind = full_stats`. **Rekor pribadi adalah perkiraan**: pace rata-rata terbaik dari lari yang minimal sejauh jarak rekor, dikali jarak itu (bukan split tercepat di tengah lari; split butuh analisis rute dan ditunda).
150. **Paspor lari:** rak medali (`passport_medals`: foto wajib + nama, opsional tanggal/kategori/event) dan hasil resmi (`passport_results`: nama event, tanggal, kategori, jarak opsional (bawaan dari kategori standar), dan catatan waktu resmi; isian pengguna, tidak diverifikasi). Keduanya bisa ditautkan ke event kalender **hanya jika pengguna menandainya ikut, event tidak diturunkan, dan tanggalnya sudah lewat** (selain itu `409 event_not_joined`); nama dan tanggal disalin agar hasil tetap utuh jika event berubah atau dihapus (`ON DELETE SET NULL`). Satu hasil per event kalender (`409 result_exists`). Event bebas (di luar kalender) boleh; tanggal tidak boleh di masa depan. Daftar event yang bisa ditautkan (dari `event_participants`, #106) ada di `GET /v1/passport/events`.
151. **Foto medali** lewat multipart (`data` = JSON, `photo` ≤ 8 MB; `fields: 1, fieldSize: 4 KB, parts: 2`), diproses `processImage` (cek isi, WebP 1600 px, EXIF/GPS terbuang) sebelum disimpan di `passport/<pengguna>/<id>.webp`, diambil lewat `/v1/passport/medals/:id/photo` dengan token dan pemeriksaan hak akses yang sama dengan paspor. Batas laju per pengguna: unggah 10/menit + **20/hari** (`MEDAL_UPLOADS_PER_DAY`, Redis, `429 medal_rate_limited`), hasil 30/menit, foto 300/menit. Batas wajar non-paket: 1.000 medali dan 500 hasil per akun.
152. **Batas medali** `MEDAL_LIMIT` di `plans.ts` (gratis 5, Premium tanpa batas), ditegakkan di transaksi dengan kunci baris pengguna (pola #43; diuji 8 unggahan bersamaan → tepat 5) dan dicek lebih awal agar gambar tidak diproses sia-sia; berkas yang sudah tersimpan dihapus jika transaksi menolak. Galat `403 limit_reached`, `limit.kind = medals` (#44). **Saat paket turun**, medali di atas batas tidak dihapus: tetap terlihat (pemilik dan orang lain) dan bisa dihapus, tetapi tidak bisa menambah sampai jumlahnya di bawah batas. Hasil resmi tidak dibatasi paket (PRD hanya menyebut rak medali).
153. **Visibilitas paspor** `users.passport_visibility`: `community` (bawaan; sesama anggota aktif satu komunitas yang tidak diturunkan, sama dengan lari #63) atau `private`. **Tidak ada pilihan publik** karena foto medali belum punya jalur laporan/moderasi; bisa ditambah bersama sasaran laporan baru. Blokir feed (kedua arah, #139) dan akun nonaktif juga menyembunyikan paspor. Tak berhak = `404 passport_not_found`, juga untuk foto medali. Orang lain melihat medali, hasil, dan lencana yang sudah didapat, tanpa info batas paket.
154. **Lencana otomatis** (`backend/src/passport/badges.ts`, fungsi murni + `BadgesService`): jarak pertama (lari pertama ≥ 1 km, 5K, 10K, HM 21,097 km, FM 42,195 km dalam sekali lari), total kumulatif 50/100/500/1.000 km, dan konsistensi 4/12/26 minggu WIB berturut-turut dengan ≥ 1 lari. **Lari sah**: ≥ 1 km dan pace rata-rata tidak lebih cepat dari 2:30/km (kendaraan atau GPS rusak). Waktu tercapai = waktu mulai lari yang memenuhinya. Lencana yang sudah didapat **tidak dicabut** walau larinya dihapus.
155. **Kapan lencana dihitung:** idempoten (`INSERT … ON CONFLICT`) dari seluruh lari pemilik, saat lari disimpan (dengan notifikasi) dan saat pemilik membuka paspornya. Lari lama sebelum modul ini **diisi otomatis saat paspor pertama kali dibuka** (tanpa migrasi data atau job). Notifikasi hanya untuk lencana yang tercapai ≤ 7 hari terakhir, jadi isian ulang dan unggahan antrean lama tidak membanjiri notifikasi. Kegagalan menghitung lencana tidak pernah menggagalkan penyimpanan lari.
156. **Lari impor (modul 2.3):** semua sumber dihitung untuk lencana pribadi pemiliknya; lencana yang **hanya** tercapai berkat lari `strava` ditandai `private_only` dan tidak pernah ditampilkan ke orang lain (dievaluasi dua kali: semua sumber dan tanpa Strava; tanda dicabut otomatis begitu lari non-Strava juga memenuhinya). Minggu berturut-turut yang ditampilkan ke orang lain juga tanpa Strava. Health Connect dan Garmin dihitung penuh; modul 2.3 perlu memastikan deduplikasi sebelum lari impor masuk agar total jarak tidak ganda.

## Modul 2.3 Impor data lari (12 Nov 2026)

160. **Health Connect = jalur utama, dibaca di HP dengan paket `health` 13.3.2, dan dipicu pengguna.** Layar "Impor data lari → Health Connect" membaca sesi lari 30 hari terakhir (batas bawaan Health Connect sebelum izin diberikan), menandai yang sudah pernah diimpor (`POST /v1/imports/health-connect/check`), lalu pengguna memilih sesi dan visibilitasnya (bawaan "komunitas", sama dengan rekaman). Tidak ada impor otomatis di latar belakang: itu butuh `READ_HEALTH_DATA_IN_BACKGROUND` dan deklarasi tambahan di Play Console, dan membaca data kesehatan tanpa tindakan pengguna tidak sejalan dengan prinsip privasi. Sesi dikirim satu per permintaan (`POST /v1/imports/health-connect`, rute maks. 15.000 titik, batas body 1 MB). Izin yang diminta hanya BACA: `READ_EXERCISE`, `READ_EXERCISE_ROUTES`, serta `READ_DISTANCE`/`READ_TOTAL_CALORIES_BURNED`/`READ_STEPS` (plugin membaca ketiganya untuk ringkasan sesi; tanpa izin itu seluruh bacaan gagal). Konsekuensi Android: `minSdk = maxOf(26, flutter.minSdkVersion)`, `MainActivity` menjadi `FlutterFragmentActivity` (plugin memakai `registerForActivityResult`), intent `ACTION_SHOW_PERMISSIONS_RATIONALE` + `activity-alias` `VIEW_PERMISSION_USAGE` (wajib Health Connect) membuka layar penjelasan data + tautan kebijakan privasi (aksi intent dibaca lewat MethodChannel `pacetara/launch`). Rute dari aplikasi lain sering butuh izin "Rute olahraga → Selalu izinkan" di Health Connect (plugin tidak bisa memunculkan dialog per sesi); aplikasi menjelaskannya dan tetap mengimpor statistik tanpa rute. `getHealthDataByUUID` tidak dipakai karena plugin me-log isi rute ke logcat di jalur itu.
161. **Statistik lari impor:** jika rute ada, rute diproses persis seperti lari aplikasi (dibersihkan, statistik dihitung server #60, zona privasi #62, terenkripsi #61) dan `runs.stats_verified = true`. Tanpa rute yang bisa dihitung (treadmill, jam tanpa GPS, entri manual), statistik yang dilaporkan sumber dipakai dengan `stats_verified = false`, setelah diperiksa: durasi 1 detik–24 jam, jarak 1 m–300 km, kecepatan rata-rata ≤ 12,5 m/s (selain itu `skipped`). **Liga dan papan peringkat (2.6) hanya boleh menghitung `stats_verified = true`.** API mengembalikan `statsVerified` di ringkasan lari.
162. **Deduplikasi antar-sumber** (`backend/src/runs/dedup.ts`): dua lari dianggap sama jika irisan waktunya ≥ 50% dari durasi lari yang lebih pendek. Prioritas **app > garmin > health_connect > strava** (app: GPS diverifikasi server dan bisa dibagikan; Garmin: sumber asli perangkat; Health Connect: agregator yang sering berisi salinan aplikasi lain; Strava: hanya riwayat pribadi). Lari baru dengan prioritas lebih rendah atau sama → dicatat `duplicate` (tidak disimpan). Prioritas lebih tinggi → lari impor yang tumpang-tindih **dihapus** (beserta fotonya; postingan feed-nya tetap dengan kartu "tidak tersedia", #137) dan catatan impornya diarahkan ke lari baru. Lari aplikasi yang diunggah belakangan (antrean offline) juga menggantikan lari impor. Pemeriksaan berjalan dalam transaksi dengan advisory lock per pengguna, jadi impor/unggahan bersamaan tidak lolos. Dengan ini syarat #156 (lencana tidak menghitung ganda) terpenuhi.
163. **Idempoten per (pengguna, sumber, id eksternal)** lewat tabel `import_records` (`imported` / `duplicate` / `skipped`, `run_id` `ON DELETE SET NULL`). Kiriman ulang = `already_imported`. Lari impor yang dihapus pemiliknya **tidak** dihidupkan lagi oleh impor otomatis (Garmin/Strava); hanya pilihan eksplisit di layar Health Connect yang boleh mengimpornya ulang. Ringkasan Garmin tanpa rute yang kemudian disusul detail beraktivitas sama melengkapi rute lari yang ada (`updated`).
164. **Strava selalu privat:** dipaksa di `ImportWriter`, ditolak saat `PATCH` (`409 strava_private`), dan dijaga constraint database `runs_strava_private`; tetap dikecualikan dari feed (#137), dan lencana yang hanya berkat Strava tetap `private_only` (#156). Lari dari paket `com.strava` yang masuk lewat Health Connect juga disimpan sebagai sumber `strava` (id `hc:<uuid>`), agar syarat Strava tidak diakali lewat Health Connect. Event `delete` dari Strava menghapus salinannya di PaceTara. Scope `activity:read_all` (agar lari "Hanya Saya" ikut; semuanya tetap privat di PaceTara). Tes e2e feed 2.1 disesuaikan karena kini lari Strava publik tidak bisa dibuat di database. **Sebelum rilis publik:** pedoman merek Strava (tombol "Connect with Strava", logo "Powered by Strava") belum diterapkan; tombol saat ini teks biasa.
165. **Garmin: OAuth 2.0 + PKCE** (`connect.garmin.com/oauth2Confirm`, token `diauth.garmin.com/di-oauth2-service/oauth/token`, `wellness-api/rest/user/id`, deregistrasi `DELETE wellness-api/rest/user/registration`) mengikuti dokumentasi migrasi OAuth2 Garmin yang kami ketahui; **alamat-alamat ini wajib dicek ulang di portal developer setelah akun PT disetujui** (semuanya terkumpul di `GARMIN` pada `backend/src/imports/garmin.ts`). Akses Starter: push saja, tanpa riwayat → tidak ada impor historis; `GARMIN_MAX_USERS` (bawaan 1.000) ditegakkan saat menghubungkan (`409 provider_full`). Lari Garmin masuk otomatis tanpa tindakan pengguna, jadi bawaannya `private`; pengguna bisa mengubahnya per lari.
166. **Keaslian push Garmin** (Garmin tidak menandatangani notifikasi): (1) endpoint memuat kunci acak `GARMIN_PUSH_KEY` (min. 32 karakter, dibandingkan waktu-konstan, salah = 404); kunci ini muncul di log akses proxy sebagai bagian path, jadi perlakukan sebagai rahasia dan ganti jika bocor; (2) hanya `userId` milik koneksi terdaftar yang diproses (dicocokkan lewat HMAC); (3) notifikasi **ping** tidak membawa data: datanya ditarik dari `callbackURL` yang wajib `https://apis.garmin.com/wellness-api/rest/…` dengan token pengguna, sehingga data pasti dari Garmin untuk pengguna itu; notifikasi **push** (data langsung) hanya diterima lewat kunci path. Data push yang mengantre di Redis dienkripsi `FieldCrypto`. Rute itu mendapat batas body JSON 15 MB (sejalan dengan Traefik #131). Notifikasi `deregistrations` menghapus koneksi.
167. **Webhook Strava** (Strava juga tidak menandatangani event): langganan divalidasi dengan `STRAVA_WEBHOOK_VERIFY_TOKEN` (GET `hub.*`), event dengan `subscription_id` selain `STRAVA_WEBHOOK_SUBSCRIPTION_ID` ditolak 403, hanya pemilik terdaftar yang diproses, dan isi event tidak dipercaya: aktivitas selalu ditarik ulang dari API Strava dengan token pengguna. Event "deauthorize" dikonfirmasi dulu ke API (`GET /athlete` menjawab 401) sebelum koneksi dihapus, agar event palsu tidak bisa memutus pengguna. Tanpa webhook, impor Strava terjadi saat menghubungkan (30 hari terakhir, maks. 30 aktivitas) dan lewat tombol "Sinkronkan sekarang" (jeda 5 menit).
168. **Pencegahan SSRF:** semua HTTP keluar ke penyedia lewat `ProviderHttp`: hanya `https` ke `apis.garmin.com`, `diauth.garmin.com`, `www.strava.com` (tanpa port/userinfo), redirect tidak diikuti (`redirect: 'error'`), batas waktu 15 detik, respons maks. 20 MB, pesan galat hanya host + status. URL dari isi webhook tidak pernah dipakai tanpa validasi; id Strava divalidasi sebagai bilangan sebelum disusun ke path.
169. **Alur OAuth di HP:** aplikasi memanggil `POST /v1/imports/{garmin|strava}/connect` (bukan GET, tanpa data pribadi di URL) dan membuka URL otorisasi di browser luar. `state` = 32 byte acak, disimpan di Redis 10 menit terikat ke pengguna (+ code_verifier PKCE untuk Garmin) dan diambil dengan `GETDEL` (sekali pakai; state penyedia lain atau kedaluwarsa = gagal). Callback ke server (`GET /v1/imports/{p}/callback`, publik), yang menukar kode, menyimpan token, lalu menampilkan halaman HTML statis tanpa JavaScript ("Berhasil terhubung… kembali ke aplikasi", `Cache-Control: no-store`, `no-referrer`) dengan tombol `pacetara://app/imports`. Skema kustom itu tidak membawa data apa pun, jadi dibajak aplikasi lain pun tidak berbahaya; aplikasi memuat ulang status saat kembali ke latar depan. Satu akun penyedia hanya terhubung ke satu akun PaceTara (koneksi lama dipindahkan).
170. **Token penyedia** disimpan terenkripsi `FieldCrypto` (AAD `import_connections.{access|refresh}:<pengguna>:<penyedia>`), id pengguna di penyedia hanya sebagai HMAC berkunci (konteks blind index baru `garmin_user`/`strava_athlete`) untuk mencocokkan webhook. Token diperbarui di bawah kunci baris (`FOR UPDATE`); token penyegar ditolak (400/401) = izin dicabut di penyedia → koneksi dihapus. Token tidak pernah masuk antrean, log, atau respons API.
171. **Worker:** antrean BullMQ `imports` (job `import`: `garmin-pull`, `garmin-push`, `garmin-deregister`, `strava-activity`, `strava-sync`, `strava-deauth`), 5 percobaan dengan backoff eksponensial 30 detik, `jobId` untuk menggabungkan notifikasi ganda, concurrency 2 (batas laju API penyedia). `WorkerModule` kini memuat `BadgesService` + `NotificationsService` (dan `RealtimeService`, yang tanpa server HTTP hanya menerbitkan sinyal Redis) agar lencana dan notifikasinya juga berjalan untuk lari impor; sinkron Strava menghitung lencana sekali di akhir.
172. **Putus sambungan** (`DELETE /v1/imports/{garmin|strava|health-connect}?deleteRuns=true|false`): token dihapus dan izin dicabut di penyedia (best effort; Garmin `DELETE user/registration`, Strava `oauth/deauthorize`); opsi menghapus semua lari dari sumber itu beserta catatan impornya (Health Connect: hanya opsi hapus lari). **Hapus akun:** koneksi dan catatan impor dihapus di transaksi yang sama, lari impor ikut terhapus lewat langkah lari, lalu izin dicabut di penyedia setelah commit.
173. **Batas laju:** impor Health Connect 60/menit, cek 30/menit, connect 10/menit, putus 10/menit, sinkron Strava 5/menit + jeda 5 menit (Redis) per pengguna; callback OAuth 20/menit, push Garmin dan event Strava 300/menit, verifikasi Strava 60/menit per IP. Semua endpoint ber-login wajib Level 1 seperti lari.
174. **Konfigurasi opsional (pola #117):** Garmin aktif hanya jika `GARMIN_CLIENT_ID`, `GARMIN_CLIENT_SECRET`, `GARMIN_PUSH_KEY`, dan URL publik API ada; Strava jika `STRAVA_CLIENT_ID`/`SECRET` + URL publik; webhook Strava jika `STRAVA_WEBHOOK_VERIFY_TOKEN`. URL publik = `API_PUBLIC_URL` atau `https://${API_DOMAIN}` (keduanya sudah ada di `.env`, diteruskan lewat `env_file`). Tanpa konfigurasi, endpoint menjawab `503 not_configured`, `GET /v1/auth/config` memberi `imports: {garmin, strava}` dan `GET /v1/imports` memberi `enabled`, sehingga aplikasi menyembunyikan kartunya. Health Connect tidak butuh konfigurasi server.
175. **Kebijakan privasi:** naskah diperjelas (bagian 4, 5, 8, 9: apa yang dibaca dari Health Connect, data yang diterima dari Garmin/Strava, Strava hanya untuk pemilik, hapus akun mencabut sambungan). **Versi tidak dinaikkan** (`2026-11-10`): naskah versi itu sudah mencantumkan Health Connect, Garmin, dan Strava sebagai sumber data dengan dasar persetujuan, dan pemrosesan baru terjadi setelah persetujuan eksplisit terpisah (dialog izin Health Connect / layar izin OAuth penyedia), sama dengan alasan #107.
176. **Belum diuji / perlu pemilik:** tes e2e memakai penyedia palsu (`FakeProviderHttp`, `FakeImportQueue`). Belum diuji: Health Connect di HP sungguhan (izin, rute dari Google Fit/Samsung/Garmin Connect), build APK dengan plugin `health` (minSdk 26, `FlutterFragmentActivity`; hanya diverifikasi di CI), Garmin dan Strava sungguhan. Pemilik perlu mendaftar Garmin Connect Developer Program (setelah kebijakan privasi tayang), membuat aplikasi Strava, mengisi env, dan saat rilis Play Store mengisi deklarasi izin Health Connect di Play Console.

## Modul 2.4 Engine event (12 Nov 2026)

177. **Antrean terpisah, bukan status di `events`:** hasil scraping dan kiriman penyelenggara masuk tabel `event_submissions` (`pending` → `approved`/`rejected`/`merged`). Tabel `events` hanya berisi event yang tayang, jadi semua kueri yang ada (`/v1/events`, kota, kartu chat, paspor, laporan) tidak perlu diubah dan tidak mungkin membocorkan event yang belum disetujui. Menyetujui = menyalin kiriman (dengan koreksi admin) menjadi baris `events` dengan `origin` (`admin`/`scrape`/`user`), `source_name`, dan `source_url`.
178. **Sumber dan tautan resmi selalu ada:** detail event (`GET /v1/events/:id`) memberi `source: {origin, name, url}`. Event manual tanpa sumber tampil "Tim PaceTara" dengan tautan pendaftaran sebagai halaman resmi. Aplikasi menulis "Sumber: <nama> · Lihat halaman resmi" (kiriman pengguna: "Sumber: <penyelenggara> (kiriman penyelenggara)"), membuka tautan di browser luar setelah memeriksa ulang `https` (#111). Panel menampilkan asal + sumber di daftar event dan bisa mengubahnya di formulir event (`sourceName`/`sourceUrl`, opsional).
179. **Kirim event hanya lewat aplikasi (pengguna Level 1)**, `POST /v1/event-submissions`; **tidak ada formulir web publik**. Situs publik tanpa JavaScript (CSP `default-src 'none'`) tidak bisa memasang captcha, sehingga formulir tanpa login hanya terlindungi batas laju per IP dan honeypot, dan akan menerima kontak pihak ketiga dari siapa saja. Level 1 (email/HP terverifikasi) memberi akuntabilitas dan pengirim bisa diberi notifikasi. Penyelenggara tanpa akun bisa mengirim lewat email ke tim. Isi formulir: data event, tautan pendaftaran (https), halaman resmi (opsional), nama penyelenggara (tampil sebagai sumber), dan kontak penyelenggara opsional (email/HP) yang dienkripsi `FieldCrypto` (AAD `event_submissions.contact:<id>`), tidak pernah ada di daftar panel, respons pengguna, atau log; super admin membukanya lewat `GET /v1/admin/event-submissions/:id/contact` yang dicatat `event_submission.view_contact` (#102).
180. **Batas laju kiriman:** 5 per 24 jam per pengguna (dihitung di database di bawah `pg_advisory_xact_lock` per pengguna agar kiriman bersamaan tidak lolos bersama; `429 submission_limit`) ditambah throttler 5/menit. Kiriman yang ditolak tetap terhitung.
181. **Tinjauan di tab "Antrean event" panel** (`/v1/admin/event-submissions?status=`, `AdminGuard`): **setujui** (`POST …/:id/approve`, body = koreksi; hasil paduan divalidasi penuh dengan skema event yang sama + tanggal tidak lampau; kota kosong dari scraping wajib diisi; nama+tanggal yang sudah ada → `409 event_exists`, gunakan gabung), **tolak** (`…/reject`, alasan 3–300 karakter yang ditampilkan ke pengirim), **gabung** (`…/merge` ke event yang tayang; event tujuan mendapat sumber/halaman resmi kiriman hanya jika belum punya). Keputusan final (`409 submission_reviewed`), dikunci `FOR UPDATE`. Tercatat `event_submission.approve|reject|merge` dengan nama, tanggal, asal, dan alasan (tanpa kontak).
182. **Duplikat ditandai, digabung oleh manusia:** daftar `pending` memuat `duplicates` per kiriman (event tayang yang tidak diturunkan dan kiriman menunggu lain) jika (a) tautan pendaftaran/halaman resmi sama setelah normalisasi (host tanpa `www.`, tanpa fragmen, parameter pelacak, dan garis miring akhir; halaman depan situs diabaikan) dengan tanggal ≤ 31 hari, atau (b) nama mirip (token dinormalisasi: tanpa aksen, tahun, kata sambung; sama persis atau Dice ≥ 0,6), tanggal ≤ 3 hari, dan kota sama (tanpa "Kota/Kabupaten"; kota kosong dianggap cocok). Tidak digabung otomatis karena seri event (mis. dua event di kota berbeda dengan nama mirip) mudah salah gabung. Dua kiriman menunggu yang sama: setujui satu, gabungkan yang lain ke event hasilnya. Fungsi murni di `event-engine/normalize.ts`, diuji unit.
183. **Scraping ulang idempoten:** unik `(source_id, external_key)`. Kunci = URL halaman khusus event dinormalisasi; jika event hanya ada di halaman daftar, kunci = nama dinormalisasi + tanggal. Upsert hanya memperbarui baris `pending` dan hanya jika ada perubahan; baris yang sudah disetujui/ditolak/digabung tidak disentuh, jadi kiriman yang ditolak tidak muncul lagi dan event yang tayang tidak berubah diam-diam (perubahan di sumber setelah tayang harus dikoreksi admin). Perubahan tanggal di sumber tanpa halaman khusus menghasilkan kiriman baru yang tertangkap sebagai duplikat.
184. **Tidak ada sumber scraping yang aktif secara bawaan** (PRD "Yang harus diverifikasi": ketentuan tiap situs belum diperiksa). Sumber diatur pemilik lewat `EVENT_SCRAPE_SOURCES` (JSON: `id`, `name`, `urls` https maks. 20, `parser` bawaan `jsonld`, `enabled`) plus `BUILTIN_SOURCES` di kode yang sengaja kosong. Konfigurasi salah = API/worker gagal start dengan pesan tanpa nilai. Worker memasang jadwal BullMQ `event-scrape` (antrean `maintenance`, tiap `EVENT_SCRAPE_INTERVAL_HOURS`, bawaan 24 jam, tanpa percobaan ulang) hanya jika ada sumber, dan menghapus jadwalnya jika tidak. Ringkasan putaran terakhir per sumber di `event_scrape_runs` (jumlah + kode galat, tanpa isi halaman), tampil di panel. Langkah pemilik (periksa ToS + robots.txt + data terstruktur, isi env) ada di README.
185. **Scraper sopan:** User-Agent jujur `PaceTaraBot/1.0 (+<PUBLIC_WEB_URL>/bot)` tanpa data pribadi, dengan halaman `web/site/bot/` (apa yang dibaca, cara memblokir). robots.txt dibaca per host sesuai RFC 9309 (grup yang memuat token `pacetarabot`, kalau tidak ada grup `*`; pola terpanjang menang, seri = Allow; `*` dan `$`), disimpan 24 jam; 4xx = boleh semua, 5xx/galat jaringan/terlalu besar = dilarang semua (disimpan 1 jam). Crawl-delay dihormati (dibatasi 60 detik), jeda minimal 5 detik per host (`EVENT_SCRAPE_DELAY_MS`), batas waktu 15 detik, halaman maks. 2 MB, robots.txt maks. 512 KiB, hanya `text/html`/JSON, tanpa kompresi dan cookie.
186. **Anti-SSRF scraper** (`ScrapeHttp`; tidak memakai `ProviderHttp` 2.3 karena itu khusus JSON dengan allowlist tetap dan `fetch` tidak bisa memeriksa IP saat tersambung): hanya `https` port bawaan, tanpa kredensial, host berupa nama domain yang ada di allowlist sumber (host dari `urls`), dan **alamat hasil DNS diperiksa saat koneksi** lewat opsi `lookup` `node:https` (semua alamat harus publik: menolak loopback, privat, CGNAT, link-local/metadata `169.254.169.254`, ULA, multicast, dokumentasi, NAT64, IPv4-mapped), sehingga DNS rebinding pun tertolak. Redirect hanya ke host yang sama (maks. 3, tetap https). TLS ≥ 1.2.
187. **Parser generik JSON-LD:** membaca `<script type="application/ld+json">` (termasuk `@graph`/daftar), node bertipe `Event`/`SportsEvent`/turunan. Dilewati: dibatalkan/ditunda, lokasi virtual, tanggal lampau atau > 2 tahun, tanpa nama/tanggal valid. Tanggal dan jam diambil apa adanya dari `startDate` (waktu setempat, tanpa konversi zona, sesuai #104). Kota dari `addressLocality`/`addressRegion` (boleh kosong). Tautan pendaftaran = `offers.url`, lalu `url` event, lalu halaman itu; halaman resmi = `url` event atau halaman itu; semuanya wajib https. Teks dibersihkan dari HTML dan karakter kontrol. Kategori jarak ditebak dari nama/deskripsi (fun/5K/10K/HM/FM/ultra, selain itu `other`) untuk dikoreksi admin. Maks. 200 event per halaman.
188. **Arsip:** event hasil engine ada di tabel `events` yang sama, jadi job `event-archive` (#106) berlaku tanpa perubahan. Job yang sama menutup kiriman `pending` yang tanggalnya sudah lewat (status `rejected`, alasan "Tanggal event sudah lewat sebelum ditinjau", tanpa notifikasi).
189. **Notifikasi ke pengirim** (pola #113–#115): kategori pengaturan baru `event` ("Kiriman event"), entri kotak notifikasi `event_submission_approved` (juga untuk gabung, karena eventnya tayang) dan `event_submission_rejected`, data hanya `submissionId`/`eventId`. Teks push memuat nama event (informasi publik); alasan penolakan hanya di aplikasi ("Kiriman saya"). Hasil scraping tidak punya pengirim, jadi tanpa notifikasi.
190. **Hapus akun:** kiriman yang belum ditinjau dihapus; yang sudah ditinjau dilepas dari akun (`submitted_by` dan kontak penyelenggara dikosongkan); event yang sudah tayang tetap (informasi publik tentang event penyelenggara, bukan data pribadi pengirim). Kebijakan privasi bagian 2 dan 9 ditambah; **versi tidak dinaikkan** (alasan seperti #107: data baru hanya diberikan sukarela lewat formulir yang menjelaskannya di tempat); pemilik bisa menaikkannya.
191. **Belum diuji / perlu pemilik:** tes memakai transport HTTP palsu (tanpa internet): robots.txt, redirect, jenis konten, jeda, idempotensi, dan SSRF tingkat URL teruji; pemeriksaan IP saat koneksi diuji lewat fungsi `isPublicAddress`, bukan koneksi sungguhan. Belum diuji terhadap situs kalender lari nyata (tidak ada sumber aktif) dan layar kirim event di HP sungguhan. Belum ada tombol "jalankan sekarang" di panel; putaran mengikuti jadwal worker. Pemilik perlu memeriksa ketentuan setiap situs sebelum mengisi `EVENT_SCRAPE_SOURCES` (README).
